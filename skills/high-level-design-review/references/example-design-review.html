Nightly Export Architecture Review

PR #87 adds a nightly export job. A Kubernetes CronJob starts an exporter that reads the day's orders from the Postgres read replica, writes them to S3 as Parquet files, checks the row counts against the source, and posts a summary to the finance team's webhook. A manifest table records every run so a failed night can be retried. This page lays out the design and assesses it for architecture, maintainability and modularization. The project, PR and numbers are made up for illustration.

Architecture

sound core, fragile edges

Works well

  • The manifest is the source of truth. It is written last, after validation, so "done" in the table means the files are complete and counted.
  • Reads hit the replica, not the primary. The connection string comes from EXPORT_REPLICA_URL and the job refuses to start against a writable database.
  • Retries are by date. Any date whose manifest row is not done is picked up by the next run, so a missed night heals itself.
  • One run at a time. concurrencyPolicy: Forbid plus a row lock on the manifest stop two pods exporting the same date.

Concerns

  • Files land under their final keys while the run is in progress. A killed pod leaves partial files that a prefix listing can't tell from a finished export. keys.py:12
  • The job reads billing's tables directly. A column rename in billing breaks the export at 02:15 with no warning to billing. billing_join.py:40
  • Chunk size is global. CHUNK_ROWS = 50_000 fits orders, but the same constant sizes the refunds pass, whose rows are ten times wider. chunker.py:9

Maintainability

well tested, some duplicated knowledge

Works well

  • Heavily tested. There are 3,050 lines of tests for 2,140 lines of code, and test_run.py walks every state transition.
  • The README maps to the code. It lists each subcommand, each manifest status and who sets it.
  • Failures say what to do. The webhook alert names the date, the failed check and the exportctl retry command to run.

Concerns

  • The same facts are kept in several places. The column list is in schema.py, orders_query.py and a test fixture; the manifest statuses are spelled out 3 times.
  • The files have no reader yet. Finance starts consuming them in #91, so the validation rules are guesses until then. validate.py:22
  • Tests mock the S3 client at the method level. A switch from put_object to the multipart helper passes every test while changing what is uploaded. test_s3_upload.py:15

Modularization

clean package, leaky boundaries

Works well

  • Small, single-purpose modules. All 14 export/ modules are under 250 lines and each does one step.
  • Imports follow the pipeline. Extraction never imports writing or reporting code; only run wires them together.

Concerns

  • The file schema is copied, not imported. schema.py restates orders.avsc by hand, and nothing fails when the two drift. schema.py:1
  • A destructive command lives next to routine ones. exportctl purge-prefix deletes every key under any prefix it is given, with no dry run and no manifest check. exportctl.py:402

5 · Non-functional requirements

Reliability, operations, security, cost

AreaAssessmentEvidence
ReliabilityGood, one gapMissed dates are retried and two runs can't overlap. The gap is the partial files a killed pod leaves (figure 2).
Operability and observabilityGoodEach step logs its row counts and duration; the webhook gets a summary or an alert with the retry command. exportctl status prints the last 14 manifest rows.
SecurityCareful, one questionThe pod's role can write only under orders/ and read only the replica. Open question: the same role is allowed DeleteObject for purge-prefix, so the nightly job can delete history it never needs to touch (export-role.json:8).
Performance and scalabilityFine for todayAbout 1.2 million rows a night in 24 chunks. Chunks run one after another, so the 2-hour deadline holds until roughly ten times today's volume.
TestabilityStrongThe checks and the state machine are pure and tested directly; S3 tests mock at too low a level (see Maintainability).
CostSmallOne pod for about 20 minutes a night and a few hundred MB of Parquet per day. No lifecycle rule on the bucket yet, so storage grows forever.

8 · To settle with the author

Open questions

  1. Can the upload go through a staging prefix, or do readers need files to appear as early as possible?
  2. Does billing offer a view or endpoint for invoices and refunds, so the job doesn't depend on its tables?
  3. Who besides an operator needs purge-prefix, and can it move out of the nightly role?
  4. Should #87 and #91 merge together, so the validation rules are checked against the real reader?
